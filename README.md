Real-Time Driver Drowsiness Detection System A non-intrusive driver monitoring system that watches the driver through a standard webcam, classifies their state in real time as awake, drowsy, yawning or distracted, and raises layered alerts when signs of fatigue appear. It runs on an ordinary laptop at 20–30 FPS with no wearable sensors, no specialised hardware and no GPU. Built as an MCA final-year project at KIIT, Bhubaneswar (January – April 2026). The problem Driver fatigue is a major cause of road accidents. Airbags, seat belts and braking systems reduce the damage once a crash has begun, but none of them prevent the crash caused by a driver whose eyes closed for four seconds. Existing approaches have real drawbacks: Physiological methods (EEG, ECG) are accurate but require sensors attached to the body, which is intrusive, uncomfortable and expensive. Vehicle-based methods (steering patterns, lane deviation) are non-intrusive but unreliable, because road conditions, traffic and weather also change how a car is driven. This project takes the behavioural, camera-based approach: watch the face, measure what the face is doing, and act on it. Features Drowsiness detection — measures Eye Aspect Ratio (EAR) to detect prolonged eye closure, with frame counters so ordinary blinking is not mistaken for sleep Yawn detection — measures Mouth Aspect Ratio (MAR) against a per-user calibrated baseline, so people with different natural mouth openness are treated correctly Distraction detection — estimates head tilt and nod angles from facial landmarks to detect the driver looking away from the road Layered alerts — a looping audio alarm, spoken text-to-speech warnings, and on- screen visual indicators Interactive quiz — on severe drowsiness the alarm stops only after the driver answers a question correctly, confirming they are actually alert Voice chatbot — a rule-based assistant that takes voice input and gives spoken safety guidance Live dashboard — real-time display of EAR, MAR, head tilt, head nod, drowsiness counter, session time, FPS and current driver state Independent detection channels — eye, mouth and head modules run in parallel, so multiple conditions can be detected at once without interfering with each other How it works Pipeline Eye Aspect Ratio (EAR) Webcam │ ▼ Frame capture and preprocessing (OpenCV: flip, brightness/contrast, BGR → RGB) │ ▼ Face detection and landmark extraction (MediaPipe Face Mesh, 478 landmarks) │ ▼ Feature computation (NumPy: EAR, MAR, head tilt / nod / yaw)

Eye Aspect Ratio (EAR)

EAR compares the vertical distances between the eyelids to the horizontal width of the eye: EAR = (‖p2 − p6‖ + ‖p3 − p5‖) / (2 × ‖p1 − p4‖) The value stays roughly constant while the eye is open (around 0.30) and drops sharply toward zero as the eye closes. Dividing by the horizontal width normalises for how far the driver is sitting from the camera, so the metric does not change just because they lean forward. A single low frame is not enough to trigger an alert — that would fire on every blink. The state is only flagged as drowsy once EAR stays below the threshold for a sustained run of frames. Mouth Aspect Ratio (MAR) MAR is computed the same way from mouth landmarks. Unlike EAR, it is compared against a per-session calibrated baseline rather than a fixed number, because natural mouth openness varies a lot between people. The system collects baseline samples at startup, then requires the reading to clear both an absolute floor and a margin above that person’s own baseline before counting a yawn. Yawn detection is also gated on the face being roughly frontal, since a turned head distorts the mouth geometry and makes MAR unreliable. Head pose Tilt is the angle of the ear-to-ear line from horizontal, nod is the angle of the nose-to-chin line from vertical, and a normalised yaw indicator measures how far the nose has moved from the midpoint between the ears. Sideways tilt suggests distraction; forward nod suggests micro-sleep. Hysteresis Each detector starts and stops at different thresholds — a condition needs a longer run of frames to trigger than it needs to clear. This prevents the state flickering on and off at the boundary, which would produce a stuttering alarm. Concurrency Text-to-speech is blocking. If it were called directly from the detection loop, video processing would freeze every time the system spoke. The solution is a single queue and a single worker thread. All speech requests go into queue.Queue() , and one daemon thread processes them one at a time. Per-channel flags prevent the same message being queued twice, and the flags are cleared in a finally block so a crash inside the speech engine cannot leave a channel permanently stuck. Only one thread ever touches the engine, so concurrent access is structurally impossible. The alarm is paused while the microphone is recording, so the chatbot can actually hear the driver’s answer. Known limitations Accuracy drops in low light or under strong glare; there is no infrared or night-vision support Eye detection is unreliable when the driver wears sunglasses or heavy frames The voice chatbot needs internet; without it the system falls back to the keyboard quiz Designed for a single driver — multiple faces in frame are not handled Detection events are not written to persistent storage Head-pose accuracy depends on reasonable camera placement Future scope High priority Offline speech recognition (Vosk or Whisper) to remove the internet dependency Infrared camera support for night driving Adaptive per-user EAR and MAR thresholds Medium priority Persist detection events to CSV or a database for analysis Mobile application for monitoring and alerts Deep-learning models (CNN) as an alternative to the rule-based detector Combine with vehicle signals such as lane position and steering Longer term Deploy on embedded hardware such as Raspberry Pi for in-vehicle installation Cloud connectivity for fleet monitoring GPS integration to suggest nearby rest stops when fatigue is detected A note on the approach This system is rule-based, not machine-learning-based. EAR, MAR and head angles are computed geometrically and compared against calibrated thresholds; no model is trained. That was a deliberate choice. Threshold logic runs comfortably in real time on a CPU, needs no training data, and — importantly for a safety system — is fully explainable: every alert can be traced back to a specific measured value crossing a specific threshold. A CNN would likely be more robust to poor lighting and occlusion, which is why it appears in the future scope, but it costs computation and transparency
